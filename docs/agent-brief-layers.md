# Бриф для агента: раскладка работы по слоям и мушиный слой

Задание на изменение `docs/tz-v2.md` и контракты для последующей реализации. Источник истины — ТЗ. Этот бриф говорит, что в ТЗ поменять и как это потом строить.

## 0. Правила работы с брифом

- Требования пронумерованы `R1…R22`, ограничения — `C1…C8`. Ссылайся на номера в коммитах и в отчёте.
- «Обязательно», «запрещено» — жёстко. «Рекомендуется» — можно отступить, обосновав в отчёте.
- Если бриф противоречит ТЗ в месте, которое бриф не велит менять, — **остановись и спроси**. Молча не выбирай.
- Числа, помеченные как «гипотеза», не записывай в ТЗ как факт. Записывай как метрику, которую надо измерить.

## 1. Цель

Каждый вопрос уходит самому дешёвому исполнителю, способному на него ответить. Для этого добавляется **мушиный слой** — разреженная ассоциативная память по алгоритму грибовидных тел дрозофилы. Он делает три вещи: ищет похожие ситуации, помнит, чем они кончались, и предсказывает исход, выдавая **удивление** как единый триггер для дорогих слоёв. Laya становится поставщиком признаков для мухи. Всё добавляется поверх: при выключенной мухе система работает ровно как в текущем ТЗ.

## 2. Ограничения — нарушать запрещено

| ID | Ограничение |
|---|---|
| C1 | **Муха аддитивна.** Флаг `FLY_ENABLED=false` возвращает поведение ровно к текущему ТЗ. У каждой функции мухи есть названный fallback — это текущий механизм |
| C2 | Муха **не зависимость пути первого звука** (§7, 70/160 мс). Заполнитель выбирается по категории от Laya, как сейчас. Муха работает параллельно |
| C3 | На критическом пути не появляется новых сетевых вызовов |
| C4 | **Воспроизводимость §3.** Любое решение мухи, меняющее поведение, сначала работает в теневом режиме. Каждое её решение логируется с кодом и версиями |
| C5 | v0 из §13 (10 пунктов) не трогать. Муха — за границей v1. В v1 добавляется только логирование (R16) |
| C6 | Правило одного писателя §4: каждая новая таблица и колонка получает писателя в таблице §4 |
| C7 | Безопасность детерминирована: чёрный список, гварды, стоп-лист, подсчёт голосов, инвалидация очереди, лестница бюджета — только код. Муха не может их ослабить или обойти |
| C8 | Моделям не отдаются вопросы, на которые код знает точный ответ. Достижимость, поиск пути, состав инвентаря — Mineflayer и код |

## 3. Не-цели — не делать в этой задаче

- Планирование, понимание слов, объяснение решений силами мухи. У неё нет слов
- Симуляцию коннектома
- Замену арбитра до прохождения критерия из R13
- Смену Голоса (Flash в v1) и бюджетов §6
- Грамматика в узле «совет → план», ослепление входа Голоса, вынос сервера на VPS и Jev как кандидат в учителя уже внесены в ТЗ (§5, §10, §12, §18; журнал, п. 43) — не переделывать и не дублировать. Jev в продакшене по-прежнему вне задачи
- Обучение на награде «интерес зрителей» — только логирование (R9). Схема наград проектируется отдельно
- Орган «момент» (когда говорить) — данных на него пока нет
- **Муха выбирает модель Голоса** (Flash, когда хватит, Sonnet, когда нужно). Запрещено: ломает правило единого голоса §6 — зрители слышат смену манеры посреди эфира
- **Несколько специализированных мух** (чат отдельно, игра отдельно). Не делать: теряются связи между областями вроде «чат взорвался, когда бот стоял у лавы». Муха одна
- **Дообучение Laya на исходах мухи.** Отложить: версии кодировщика начинают зависеть друг от друга по кругу (R4), а выигрыш скромный

## 4. Принцип маршрутизации

| Слой | Отвечает на вопрос | Цена | Структурно не умеет |
|---|---|---|---|
| Код | «сколько, где, можно ли» — точный ответ | 0 мс, €0 | ничего приблизительного |
| Муха | «бывало ли похожее и чем кончилось» | < 1 мс, €0 | слова, смыслы, планы |
| Laya | «что это за текст» | 30 мс, €0 | опыт, последствия |
| Облако | «как это сказать, куда двигаться дальше» | секунды, деньги | быть дешёвым |

Правило: вопрос не отдаётся слою дороже необходимого и не отдаётся слою, который на него структурно не отвечает.

## 5. Контракты

### 5.1 Вход мухи

**R1. Вектор признаков** на каждое событие, два блока.

*Блок text.* Вектор, который подаётся на головы решений Laya — выход пулинга бэкбона, не последний слой головы. Размерность брать из `config.json` чекпойнта (для mmBERT-base ожидается 768 — проверить, не хардкодить). L2-нормировать. Для событий без текста (игровые, смерть, донат без сообщения) — нулевой вектор.

*Блок game.* Фиксированная схема `FEATURES_V1`, около 50 чисел. Каждое стандартизуется бегущими средним и дисперсией, замороженными на версию кодировщика. Состав:

| Группа | Признаки |
|---|---|
| Сырое состояние | здоровье, голод, время суток, освещённость, биом (бакет), число угроз, дистанция до ближайшей, флаги ключевого инвентаря |
| Событие | one-hot типа события, источник (`game / chat / donation / voice / timer`) |
| Производные | Δздоровья за 3 тика; смертей за час; смертей от того же убийцы; отношение темпа чата 10 с / 60 с; бакет доверия автора; исходы трёх последних советов автора; провалов этой пары `(намерение, цель)` сегодня; секунд с последней реплики Голоса; число активных эффектов; активна ли обсессия |

Производные считаются кодом и SQL из уже существующих таблиц: `deaths`, `skill_credits`, `utterances`, `triggers`, `viewers`, `effects`, `obsessions`. Модели для них не нужны (C8).

**R2. Проекция.** 2000 клеток. Каждая клетка суммирует **стратифицированно**: 6 случайных измерений блока text и 4 случайных измерения блока game (параметры конфигурируемые). Иначе блок text на 768 измерений задавит блок game на 50 при равномерной выборке. Матрица бинарная и разреженная, сид фиксирован, матрица сохраняется вместе с версией кодировщика.

**R3. Нормализация — обязательно.** Winner-take-all: активны ровно `k = 100` клеток с наибольшими суммами, остальные гасятся. Без этого «громкие» ситуации зажигают сотни бит, а тихие — десятки, и коды перестают сравниваться. В мухе это делает тормозной нейрон APL; при его отключении муха перестаёт различать похожие стимулы, сохраняя различение непохожих. На выходе: 2000-битный код, ровно 100 единиц.

### 5.2 Версионирование кодов

**R4. `ENCODER_VERSION`** = хеш от: схемы `FEATURES_V1`, статистик стандартизации, сида проекции, **идентификатора чекпойнта Laya**. Любое изменение делает все старые коды несравнимыми с новыми. Поэтому:

- логируются исходные данные для пересчёта: вектор блока game на каждое событие и ссылка на текст события;
- при смене версии история перекодируется офлайн, индекс перестраивается, веса мухи переобучаются проигрыванием залогированных исходов; переключение — только после завершения перестройки;
- **файнтюн Laya по §18 меняет блок text и тем самым обесценивает все коды.** Каждое обновление Laya проходит перекодирование до выкатки. Это надо записать в §18 явно — иначе первая же дообученная Laya тихо сломает память мухи.

### 5.3 Хранилище и индекс

**R5. Таблица `fly_codes`**: `{event_id PK, ts, session, encoder_version, code BLOB(250), game_features BLOB, outcome, outcome_ts}`. `outcome` — значение из R10, заполняется по истечении горизонта. Писатель — Диспетчер (муха работает в его процессе). Объём: около 0.5 КБ на событие, порядка мегабайта за эфир.

**R6. Индекс в памяти.** Инвертированный: бит → список `event_id`, по последним 100 000 кодам текущей версии (около 40 МБ, укладывается в запас бюджета §5). Перестраивается из SQLite на старте. Запрос: top-k по числу общих активных бит, при равенстве — по свежести. Бюджет: 5 мс p50 / 15 мс p99, выполняется параллельно со сбором контекста (§7, `Promise.all`).

### 5.4 Отбор контекста для §9

**R7.** Основной путь отбора контекста в промпт — похожесть, а не свежесть: пять самых похожих прошлых событий → join к `facts`, `utterances`, `deaths`, исходам навыков → блок 2 порядка сборки промпта (§8).

- Этап тени (C4): оба набора — по похожести и по SQL — считаются и логируются, в промпт идёт SQL, пока автор не оценит 30 выборочных промптов. Дальше похожесть становится основным путём
- Холодный старт: меньше 200 кодов текущей версии → текущий SQL по свежести и весу
- Муха выключена → текущий SQL
- Гипотеза, а не факт: похожесть даёт более уместный контекст. Метрика: оценка автором уместности на 30 выборочных промптах, похожесть против свежести

### 5.5 Валентность

**R8. Веса** хранятся на бит, на валентность, на орган. Валентности в этой задаче:

| Валентность | Источник | Обучается |
|---|---|---|
| Опасность | урон и смерть — события кода | да |
| Успех | постусловие попытки навыка §10 | да |
| Интерес зрителей | реакция чата на реплику | **нет, только лог** (R9) |

Две временные шкалы на валентность: быстрая (гаснет примерно за эфир) и медленная (растёт, только если быстрая уже выше порога — консолидация требует повторения). Поведение читает сумму двух.

**Хранение весов — обязательно.** Снапшот весов пишется в таблицу `fly_weights` с версией `weights_version` на каждую сессию и после каждой ночной консолидации (R21). Каждое решение мухи логируется с `encoder_version` и `weights_version` — без этого §3 не выполняется: решение нельзя воспроизвести.

**R9. Следы приемлемости.** Каждый источник награды объявляет окно кредитования: опасность — 30 с до события; успех — от старта попытки до постусловия или таймаута навыка. Вес следа `exp(−Δt / τ)`, `τ = окно / 3`. Обновление: `w_b += η · r · trace_b` по активным битам, с клиппингом. Для интереса зрителей в `utterances` логируются сырые сигналы (темп чата до и после реплики, число ответов с упоминанием бота), обучения нет.

### 5.6 Предсказание и удивление

**R10. Закрытый набор исходов**, горизонт 30 с после события, при нескольких побеждает первый по порядку: `death`, `significant_damage`, `skill_success`, `skill_fail`, `item_gained`, `donation`, `chat_spike` (темп ×3 за 10 с против 60 с), `nothing`. Предсказание: `p(o | code) = normalize(Σ_{b ∈ активные} (c_b[o] + α))`, `α = 1`. Счётчики `c_b` обновляются, когда исход размечен.

**R11. Сигналы.**

- `novelty = 1 − max_overlap / 100` по индексу — работает с первого события
- `surprise = −log p(наблюдаемый исход | код)` — только после 500 размеченных событий текущей версии; до этого используется `novelty`
- Триггер: сигнал выше бегущего 95-го перцентиля по последним 1000 событиям. Порог калибруется сам
- **Страховка стоимости:** облачные пробуждения по триггеру — не чаще раза в 20 с, учитываются в окне Казначея §6; первая ступень лестницы §6 отключает пробуждения по удивлению
- Каждый триггер логируется: код, значение, порог

### 5.7 Потребители сигнала

**R12. Наблюдатель** просыпается по триггеру, а не раз в 30 с. Нижняя граница 20 с, верхняя 120 с (проснуться в любом случае, чтобы сводка не протухала). Муха отбирает пять самых значимых событий с прошлой сводки, Flash пишет сводку только по ним. Fallback — таймер 30 с. Этап тени (C4): первый эфир Наблюдатель работает по таймеру, а муха логирует, когда разбудила бы его и какие пять событий выбрала; сравнение — на стенде R18. Гипотеза: вызовов в час около 30–40 вместо 120. Метрика: вызовы в час и входные токены на вызов до и после; оценка автором 20 сводок не должна упасть.

**R13. Приоритет — только теневой режим.** Муха считает выученный приоритет, решает по-прежнему арбитр с явными весами. Оба значения пишутся в `arbiter_log`. Критерий переключения: на трёх эфирах подряд ранжирование мухи лучше согласуется с разметкой автора, чем веса арбитра. Переключение — флагом и сменой версии весов.

**R14. Режиссёр.** Кандидаты в клипы — объединение текущего списка поводов (он остаётся: воспроизводим и гарантирован) и событий с сигналом выше 99-го перцентиля или с модулем валентности в верхнем 1%. Метрика: доля размеченных клипов, которые автор оставил, отдельно по источнику — правила против мухи. Поведение эфира R14 не меняет — только добавляет строки в `clips`, — поэтому этап тени ему не нужен.

### 5.8 Laya на полную

**R15.**

- Один прямой проход на сообщение даёт и метки голов, и вектор для R1. Вектор кешируется по `event_id` и хешу сообщения — тот же кеш потом обслужит «кеш решений по хешу» из оптимизаций второй очереди §7
- Критический путь не меняется: батч 1, 30 мс
- **Рекомендуется, при условии:** Jev как учитель дистилляции в §18 вместо `teacher_flash` с выборкой одно из двадцати — мягкие метки на каждое событие, новое значение `decided_by = teacher_jev`, к меткам подмешиваются реальные исходы §10. **Условие — условия TypeSafe разрешают дистилляцию в собственные веса. Проверить до любых правок; если запрещено или неизвестно — пункт пропустить и написать об этом в отчёте**

### 5.9 Единственное, что входит в v1

**R16.** Строка в плане v1: логировать вектор блока game (`FEATURES_V1`) на каждое событие и сырые скоры **проигравших** кандидатов в `arbiter_log`. Причина: муха строится после v1, а производные признаки задним числом не восстановить. Проигравшие кандидаты — бесплатные контрфактические данные для R13. Цена — около 200 байт на событие.

### 5.11 Расширения: где слои начинают кормить друг друга

**R18. Стенд переигровки.** Расширяет «режим прогона по файлу» из §13.

- Вход: записанный эфир — события, векторы признаков (R16), `arbiter_log` с проигравшими кандидатами, исходы
- Прогон: диспетчер, арбитр и муха с конфигурацией А и с конфигурацией Б на одном и том же логе. Конфигурация — флаги, версии, пороги
- Выход — отчёт: выбор А против Б в каждой точке решения; согласие с залогированными исходами; согласование приоритета с разметкой автора; число и калибровка срабатываний удивления; число пробуждений Наблюдателя; наборы отобранного контекста для оценки автором; оценка стоимости облачных вызовов
- **Детерминизм обязателен:** один лог и одна конфигурация дают побайтно одинаковый отчёт
- **Ограничение — записать в ТЗ прямо:** переигровка оценивает только первое решение. Последствия не воспроизводятся — после другого решения мир пошёл бы иначе. Поэтому переигровка **отсекает** плохие варианты до эфира, но включение поведения по R13, R19, R20, R22 по-прежнему решается живыми эфирами

**R19. Выбор версии плана по ситуации.** В §10 у пары `(намерение, цель)` бывает несколько версий плана. Сейчас версия выбирается по правилу «последние попытки успешны» — без учёта ситуации.

- Орган — версия плана. Веса на бит на версию, обучаются валентностью «успех» (R8) со следами (R9)
- Выбор: версия с наибольшим предсказанным успехом для текущего кода. При разнице ниже порога — текущее правило §10. Случайного исследования нет: оно ломает воспроизводимость §3
- Этап 1, тень: муха пишет свой выбор рядом с выбором правила. Где выборы совпали, исход засчитывается обоим
- Этап 2, узко: муха решает только там, где версия по правилу **уже проваливалась в похожей ситуации** (перекрытие кодов выше порога) за последние N попыток
- Расширение: успешность попыток, выбранных мухой, не ниже, чем у правила, минимум на 20 попытках
- Fallback — текущее правило §10

**R20. Вопрос чату при неуверенности мухи.** Сейчас бот спрашивает чат только при отсутствии навыка. Добавляется второй повод.

- Условия — все одновременно: решение выбирает между вариантами с разными предсказанными исходами (лезть ли в пещеру, драться или бежать, какую версию плана); предсказанные шансы на хороший исход у вариантов различаются меньше порога δ; прошёл холодный старт (R11: не меньше 500 размеченных событий — иначе неуверенно всё, и бот будет спрашивать непрерывно)
- Ограничения: не чаще раза в пять минут; не пока ждёт подтверждения другой план (§10, «открытый план ровно один»); не в защищённом окне §17; варианты сначала проходят чёрный список §10 — необратимое не предлагается никогда (C7)
- Механика: варианты раскладываются по корзинам уже существующего счётчика (§16), окно 20–30 с, кворум — два уникальных аккаунта. Нет кворума — решает сам по слабому предпочтению мухи или по правилу
- **Учит мир, а не голосование.** Валентность обучается только исходом выполненного варианта. Сам голос логируется, но в обучение не идёт. Отсюда защита от троллей: они могут заставить бота сделать глупость — это контент, — но не могут испортить ему память
- Этап тени: первый эфир — только лог «здесь спросил бы», чтобы проверить частоту
- Метрика: падает ли неопределённость предсказания в похожих ситуациях после вопросов быстрее, чем без них

**R21. Ночная консолидация.** Запускается в постстрим-конвейере §17 после бэкапа, асинхронно и с ретраями, как весь конвейер.

1. Если сменилась `ENCODER_VERSION` — перекодирование истории и перестройка индекса (R4)
2. Проигрывание событий сессии с уже известными исходами: медленные следы пересчитываются детерминированно, быстрые гасятся к базовому уровню
3. Прореживание индекса до лимита R6
4. Отчёт «что поменялось за ночь»: события, у которых предсказанная валентность сильнее всего сдвинулась между началом и концом сессии. Отчёт уходит Летописцу как материал для эпизода и recap. Если Летописца ещё нет (он за границей v1), отчёт просто хранится
5. Снапшот весов в `fly_weights` с пометкой `consolidated`

Старт §17 проверяет: версия индекса равна `ENCODER_VERSION`, последний снапшот весов консолидирован. Нет — эфир стартует с выключенной мухой (R17). Цена: процессор ночью, ноль денег на API.

**R22. Предварительное доверие новичку по похожести.** За границей v1, вместе с системой доверия. Решает открытую проблему §10: «новичок с хорошим советом не проходит».

- Представление зрителя: среднее L2-нормированных векторов блока text (R1) по его последним N сообщениям. Колонка `style_vec` в `viewers`, писатель — Архивариус
- Новичок — меньше K оценённых советов. Его предварительное доверие: взвешенное по похожести среднее доверия десяти самых похожих ветеранов, только положительная часть — `max(0, ·)`
- **Жёсткие ограничения, иначе это профилирование людей по стилю речи:**
  - предварительное доверие только поднимает приоритет, с которым бот слушает совет. Оно **никогда** не засчитывается в подтверждения выполнения и **никогда** не заменяет «доказанное доверие» из §10
  - похожесть **никогда не опускает** доверие. Понизить его могут только собственные поступки человека
  - заменяется собственным доверием, как только у зрителя набирается K оценённых советов
  - на оверлеи §15 не выводится
- Этап тени: логировать предварительное доверие и что изменилось бы в порядке, до включения
- Метрика: успешность советов новичков, получивших поднятый приоритет, против остальных

## 8. Инварианты ТЗ после правок

- У каждой таблицы §8 есть писатель в §4
- Реестр голов Laya ровно один
- Нет ссылок `§N` на несуществующие разделы

- Сумма бюджета первого звука §7 не изменилась
- У каждой функции мухи назван fallback
- Голоса чата не обучают валентность напрямую — только исходы выполненных действий (R20)
- Предварительное доверие не засчитывается в подтверждения выполнения и не понижает доверие (R22)
- Любое решение мухи, меняющее поведение, имеет описанный этап тени (C4)

## 10. Гипотезы, а не факты

Не записывать в ТЗ как утверждения, только как метрики к замеру:

- похожесть даёт более уместный контекст, чем свежесть
- Наблюдатель по удивлению тратит в разы меньше при той же полезности
- удивление полезнее таймера как повод будить облако
- производные признаки поднимают качество мухи сильнее, чем любые правки алгоритма
- выбор версии плана по ситуации успешнее выбора по последним попыткам
- вопросы чату при неуверенности снижают неопределённость быстрее пассивного накопления
- после ночной консолидации предсказания на следующем эфире точнее
- поднятый приоритет новичков увеличивает число принятых хороших советов, не увеличивая провалы
